# Topic visibility and locality on Linux

Status: **draft** (2026-11-09). Implements, for the Linux realizer, the
contract grammar in ros-launch-manifest `docs/design/visibility-and-exports.md`.
The board realizer's companion is nano-ros RFC-0125.

## What the contract gives us

ros-launch-manifest adds `exports:` on a manifest scope (a `<stem>.contract.yaml`
beside a launch file, or an inline include) and a `visibility:` shorthand per
topic. The resolver records each topic's `visibility` and whether it is
`closed`, and the crate's `locality(model, placement, grouping)` returns one
class per topic: `local`, `host`, `bounded(<scope>)` or `open`.

play_launch is the realizer that knows the `grouping` on Linux: which nodes
share a process (a component container) and which host each process runs on.
This document says what play_launch does with each class.

## Grouping: containers follow the scopes

Today a container's membership is whatever the launch file wrote. With
visibility, play_launch may DERIVE it, when the author allows:

- A closed scope whose nodes are all composable is a candidate container. Its
  internal topics become `local` when the scope is loaded into one container.
- This is opt-in per scope (`launch: compose_internal: true` in the scope's
  play_launch section, not in the contract, because process layout is this
  realizer's fact, not a model fact). Without it the launch file's own
  container layout stands and locality is computed from it.
- A container derived this way enables `use_intra_process_comms` for its
  nodes.

## Tier 1: send only while someone remote listens

rclcpp with intra-process enabled already publishes inter-process only when
`get_subscription_count() > get_intra_process_subscription_count()`. So Tier 1
on Linux is: put the scope's nodes in one container with intra-process on.
Nothing else is needed, and a `ros2 topic echo` started later is an ordinary
remote match.

For rclpy nodes and for nodes play_launch cannot compose, Tier 1 is not
available; their topics stay on the wire and the locality report says so.

## Tier 2 on Linux

A `local`, closed, non-public topic in a container could skip its RMW
publisher altogether, but rclcpp has no supported way to create an
intra-process-only publisher. So Tier 2 on Linux is limited to what the RMW
can be told:

- **rmw_zenoh:** play_launch generates the session config for the container
  with the scope's internal topics denied in the ACL for egress, so they are
  never sent off the process even if a remote subscriber matches. The
  liveliness token still exists; `ros2 topic list` shows the topic, and an
  `echo` gets a clear refusal through the monitor (below), not silence.
- **DDS (Cyclone, Fast DDS):** the scope's internal topics are placed in a
  per-scope partition generated by play_launch; nothing outside the scope
  joins it.

## Bounded topics: generate the boundary configs

For `host` and `bounded(<scope>)` topics, play_launch writes every boundary
configuration from `exports`, and none is hand-written:

| boundary | generated from `exports` |
|---|---|
| `rmw_zenohd` router | ACL: deny egress beyond the scope's hosts for its non-exported topics |
| zenoh-bridge-ros2dds / DDS Router | allowlists: exactly the exported topics, per direction |
| `domain_bridge` | its YAML topic list |
| discovery | `ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST` for a process whose topics are all `host`-local or narrower (DDS only) |

A generated file is a build artifact; the launch prints where it wrote it.

## Monitoring: enforce, and suggest

The live entity monitor already sees the runtime graph. It adds two reports:

- **Violation:** a subscriber or publisher outside a scope on a non-exported
  topic. Reported with the topic, the scope, the consumer node and the host,
  at the moment it matches, instead of a topic that silently delivers nothing.
- **Suggestion:** after a run, the public topics that never had a consumer
  outside their scope. These are candidates for `exports`, with the run's
  evidence. play_launch never writes the contract itself.

## Debug switch

`play_launch launch ... --expose <scope>` treats the scope as open for this
session: no ACL denial, no partition, and the locality report states that the
optimization is off. The contract does not change.

## Locality report

`play_launch locality <launch>` prints, per closed scope: exported topics,
internal topics, and each internal topic's class and what it saved (wire
skipped, restricted, or neither, and why). A change that turns a `local` topic
into `open` shows up as a diff of this report in review.

## Work

1. Read `visibility`/`closed` from the model; call the shared `locality()`.
2. Container derivation for `compose_internal` scopes.
3. Boundary config generation (zenohd ACL first, then bridges).
4. Monitor violation + suggestion reports.
5. `--expose`, `play_launch locality`.

## Open questions

1. Is an ACL egress deny on rmw_zenoh enough for Tier 2, or should
   play_launch also drop the liveliness token (which needs rmw_zenoh support)?
2. Should container derivation ever be the default, or always opt-in?
